# IMPACTS Architect

Owns: the invariants list, mode selection, the topology path, build routing, restructuring, import, the walk test and guardrails. Reader: author. Does not own: form selection, see [ICM form selection](references/formwahl.md).

For first use or unresolved source identity or links, follow [Version and entry points](../../README.md#version-and-entry-points). Use the complete corresponding protocol source; this skill folder alone lacks required parent protocol files and root guidance. If that README is missing, recover the original source/revision from the copy's provenance: obtain a published revision from [releases](https://github.com/Melvinanalytics/impacts-protokoll/releases), or an unreleased revision from its recorded original repository or file snapshot. If provenance is unknown, keep the revision open and resolve the source before applying missing rules; do not select the latest release as a substitute.

This skill selects the smallest fitting ICM form, then produces only the files that form needs. For a Pipeline using Core contracts, the core validates a Hauptprozess tree of `CONTEXT.md` files. Other forms use the workspace's native routers, `grundlagen/` and `records/` where real content requires them. The Architect role prepares and reviews definitions and evidence; it never executes an Arbeitsschritt or completes a human gate. Decision origin and recording by a configured executing harness follow [Signals and human gates](../binding.md#signals-and-human-gates). The skill never introduces a schema, field or folder kind the core does not have.

For a requested interview, start at [Guided interview](../impacts-method.md#guided-interview) before form selection. For other work, start with the [formwahl work report](references/formwahl.md#work-report-before-proposing-a-tree), including its business-capture branch. For a Pipeline, load the [capture/build method](../impacts-method.md#capture-business-meaning) and the phase section in use; load the [decomposition rules](references/zuschnitt.md#arbeitsschritt) when cutting work and the [automation boundary](references/zuschnitt.md#automation-boundary) when assigning contributions. For reusable operations, load the [Capability contract](../capabilities.md) and its relevant [extraction/call rules](../capabilities.md#when-to-extract). Load [source](../binding.md#snapshot-and-provenance), [handoff](../binding.md#visible-output-and-handoff), [writeback](../binding.md#record-writeback) or [Gate](../binding.md#signals-and-human-gates) rules only when that branch is present, including work without an extracted Capability. For every form, use the linked [evidence labels](../ontology.md#evidence-and-obligations) and [UX/AX/DX acceptance](../impacts-method.md#readability-and-processing).

Before capturing, changing or applying domain meaning in any form, read [Author or change](../ontology.md#author-or-change) or [Use](../ontology.md#use), then apply the ontology's [evidence and obligations](../ontology.md#evidence-and-obligations) and [enforcement/completion](../ontology.md#enforcement-and-completion). Routine use does not recapture the model; Core validity alone does not establish domain correctness. For catalog, pipeline and document-template composition, follow the [worked company example](references/datenbezug.md#from-catalog-through-pipeline-to-a-filled-offer).

Resolve the customer’s [working language](../language.md#select-and-bind) before capture or import. Use localized templates (`--language de` for German-only work); keep all customer-readable instructions, drafts and decision requests in that language. Apply the actual [language/meaning check](../language.md#enforce-at-use-boundaries) before customer use.

## Invariants

Hauptprozess/Vorgang-specific invariants apply to selected Core contracts, as the [Tooling stop](references/formwahl.md#tooling-stop) defines.

1. One Hauptprozess has one embedded process Leistung. Two independently bounded process results mean two Hauptprozesse; catalog items are not Hauptprozess boundaries.
2. Arbeitsschritte own their routes, the Hauptprozess owns the entry, every Arbeitsschritt reaches a named end.
3. The Hauptprozess tree holds only `CONTEXT.md` files. Foundations live where their [data kind](references/formwahl.md#data-kinds) places them, and records in their designated systems or `records/`. Reusable processing lives in Fachrepo- or Workspace-level `capabilities/<slug>/`, code otherwise in dependencies.
4. For Core Vorgänge, the workspace root is the Git root. A Vorgang binds a committed Hauptprozess tree.
5. `gate: human` follows the [reserved-decision criterion](references/zuschnitt.md#arbeitsschritt).
6. Apply [Hauptprozess and Vorgang separation](../../AGENTS.md).
7. Every claim carries its source and the evidence label defined in the [ontology](../ontology.md#evidence-and-obligations); a confirmed document does not confirm every interpretation of it.
8. `impacts validate .` checks the selected Core Hauptprozesse and Vorgänge, not non-process knowledge topology or arbitrary domain meaning. Apply it for the needed condition, as the [Tooling stop](references/formwahl.md#tooling-stop) bounds it.

## Form selection

For work being set up or materially redesigned, first derive the intended result and necessary contributions through [reverse engineering](../impacts-method.md#reverse-engineer-a-product-or-service) before selecting a form or executor; this does not require an established Pipeline or Build mode. Before proposing a tree, complete the work-report recipe in [formwahl.md](references/formwahl.md#work-report-before-proposing-a-tree) using that derived boundary. Select the smallest fitting form from the units that grow or repeat and the bounded results whose steps can be declared: Pipeline, Record Library, Knowledge Bundle, Context Map, Umbrella or System Map. Enter Build mode only when the selected form is a Pipeline using Core Hauptprozess contracts. Ordinary process guidance reuses existing homes under [Tooling stop](references/formwahl.md#tooling-stop); it does not require Build mode. For a non-process form, build only its native Markdown topology and use the applicable walk branch below.

## Choose a mode

- A requested interview about a business, offering, founder idea or recurring job: [Guided interview](../impacts-method.md#guided-interview), before choosing a file or process form.
- A selected Pipeline that will become a Hauptprozess, described in conversation with no folder yet: Build mode.
- A newly described Record Library, Knowledge Bundle, Context Map, Umbrella or System Map: Topology path.
- An existing customer folder, repository or vault, or a declared set of repositories: Restructure mode, then route each found form through its selected path.
- An approved Hauptprozess in a Fachrepo: Import mode.

## Topology path

For a newly described Record Library, Knowledge Bundle or Context Map, create only populated native Markdown homes and links under its rules. Run its Knowledge Walk when the topology uses `records/` or domain `grundlagen/`; if a Context Map links only Hauptprozesse, run the Process Walk for each linked Hauptprozess. Add no checker or runtime.

For an Umbrella, create a small router to multiple independent Pipelines; selected Core Hauptprozesse use their Process Walks.

For a System Map, use the existing repository map and files, then select and test its child forms through their applicable walk branches.

## Build mode

For selected Core Hauptprozess/Vorgang contracts, follow the method's phases in order; load each linked section when doing that work. Reuse the form-selection evidence and fill the existing Hauptprozess template sections.

1. [Identify](../impacts-method.md#identify). Use [reverse engineering](../impacts-method.md#reverse-engineer-a-product-or-service) for supplied products/services and for work being set up or materially redesigned from an intended result. For new observations without a suitable home, use [ist-prozess.md](templates/ist-prozess.md) or its [German counterpart](templates/de/ist-prozess.md) under `analyse/`.
2. [Minimize](../impacts-method.md#minimize). Record each proposed move and its decision in the analysis file's Analysis table; the definition carries only what is kept.
3. [Perfect](../impacts-method.md#perfect). Use [Leistung and decomposition](references/zuschnitt.md) to cut the supported work into the existing tree.
4. [Augment](../impacts-method.md#augment). Close the minimum point-of-use context, its acquisition or derivation, freshness/control, destination and missing-context route for each retained contribution; then select contributions through the [automation boundary](references/zuschnitt.md#automation-boundary). Load Capability [extraction](../capabilities.md#when-to-extract) and [call](../capabilities.md#capability-call) rules only when applicable.
5. [Construct](../impacts-method.md#construct). Use `impacts template <kind>` or its existing template at the [analysis or definition home](references/formwahl.md#data-kinds). Build mode is incomplete until every Hauptprozess, Teilprozess and Arbeitsschritt retains its role-specific sections and satisfies its localized setup-completion section under [Maintain agent instructions](../impacts-method.md#maintain-agent-instructions). Complete [Arbeitsschritt composition](../impacts-method.md#compose-an-arbeitsschritt) and the [workspace/harness setup](references/formwahl.md#native-topology-and-boundaries). Before claiming Core structural conformance, run `impacts validate <hauptprozess-folder>` and correct failures under [Tooling stop](references/formwahl.md#tooling-stop). Use the [analysis-to-definition placement](references/formwahl.md#data-kinds) for candidates and confirmed Hauptprozesse. Commit the selected tree. `git rev-parse HEAD:<hauptprozess-folder>` identifies the tree that the Test phase's responsible harness exercises and new Vorgänge bind.
6. [Test](../impacts-method.md#test). Apply the selected walk branches below. The Architect prepares and reviews; when Core execution is selected, the responsible harness exercises representative Vorgänge within their declared authority.
7. [Scale](../impacts-method.md#scale). For use in Core Vorgänge, commit the tested revision. Follow [Reviewed correction](../impacts-method.md#reviewed-correction) for subsequent changes in any form.

## Restructure mode

1. Inventory, touch nothing. Name each declared repository, its actually bound protocol source/revision and intended comparison revision. Record whether inspected files are committed or explicitly captured working states; preserve others' changes. List the relevant tree and, per area, what it is, when last touched and what refers to it. The declared repositories bound discovery; they do not prove that every outside consumer is known.
2. Find the hidden forms before hidden Hauptprozesse. Ask which units grow or repeat, what result is accepted and whether its steps can be declared. Select each repository's forms with the [formwahl work report](references/formwahl.md#work-report-before-proposing-a-tree), then apply [Composition](references/formwahl.md#composition). For each Pipeline, ask where work enters and leaves; interview the folder the way you would interview the person.
3. Classify affected files by the [existing homes](references/formwahl.md#native-topology-and-boundaries). Retain non-Capability code at its existing `tools/`, `src/` or dependency home outside the Hauptprozess. For each shared or moved meaning or executable contract, name its authoritative repository, responsible source owner if evidenced, source path or URI, bounded revision, scope and evidence state; leave an unknown owner open. Identify each known consumer's actual source/revision and whether it links, pins, copies, adapts, projects, installs or executes the source. A link or installation depends on a reachable target; a pin fixes a revision; a copy or adaptation has its own local revision and claims; a projection derives from a source; execution consumes a declared input/output contract. A matching name, bytes or repository owner does not establish claim-level authority; different local scopes or premises may legitimately retain different meanings. Mark superseded, duplicate or unreferenced files for retirement only after the reference check; Git history preserves them without an archive folder.
4. Reference check before any move: inspect relevant in-repo links and sibling paths, code imports, scripts, jobs, package references, installed symlinks and known consuming repositories. Ask the source owner and affected consumer owners about references the local scan cannot see. Record the repositories and surfaces actually searched, found referrers and unresolved outside-consumer boundary. A bounded search never proves the absence of external consumers. A live referrer must stay supported or move with its consumer. An identified but unverified outside reference is a specific unresolved lead; hold retirement until that lead is resolved or a supported compatibility path covers it. The general possibility of undiscovered consumers is residual uncertainty, not a specific lead.
5. Classify each proposed change separately: physical path move, changed domain meaning or valid inference, protocol-revision upgrade, and changed consumer input/output contract can coincide but do not certify one another. For changed meaning, follow [Author or change](../ontology.md#author-or-change) and its valid, missing/conflicting and forbidden-inference cases. For an approved Core Hauptprozess transfer, follow [Import mode](#import-mode). For an in-place definition change, follow [Reviewed correction](../impacts-method.md#reviewed-correction); check compatibility against the actual target protocol revision under [Review another Fachrepo](../impacts-method.md#review-another-fachrepo). A byte match proves only copy identity.
6. In the existing review or case home, prepare a migration map for human approval: old and proposed source/revision, owner, scope/evidence, role, known consumers/referrers and dependency kinds, change kinds, each affected consumer check, unresolved blockers and recovery path. State which independent parts may proceed. Migrate only after the required human authorization for the affected scope, including authorization already supplied for the concrete change. Do not write a fictional `human:<id>` approval.
7. Migrate by copy, verify, then conditionally remove: check case-folded destination collisions, copy, then compare file count and hashes where claiming copy fidelity. Separate Git roots cannot change atomically; stage consumer updates and retain the old path or definition until each live use passes its needed check or a supported compatibility route covers it. On failure, restore the previous route from the retained source and bound revision. Do not retire while a specific outside-consumer lead remains unresolved. After a documented bounded search with no such lead, record its coverage and residual uncertainty; the responsible source owner decides within the step 6 authorization whether to retire with the recovery path or keep a stated compatibility period. Neither choice establishes that no other consumer exists.
8. Rebind each changed consumer explicitly to the target source/revision. Check its declared needed meaning, permitted use, input/output contract and applicable validator against that revision; a link or structure check proves only its own condition. Keep earlier bound Vorgänge and inputs unchanged. A missing source or incompatible contract blocks the dependent use. Independent preparation continues.
9. Route every found form: Build mode only for Hauptprozesse and Topology path for non-process forms. Apply needed Core checks under [Tooling stop](references/formwahl.md#tooling-stop), then the applicable walk-test branch for each selected form. For a cross-repository change, also run a fresh reader from each relevant repository entry to the authoritative source and affected consumer handoff. Record loaded paths, actual revisions, answer points, unsupported conclusions, executed checks and open gaps. Report an unavailable check as missing under [Tooling stop](references/formwahl.md#tooling-stop). Do not claim lower token use, coherence or migration safety without a matched, measured baseline.

## Import mode

1. Check the declared source and target protocol revisions under [Review another Fachrepo](../impacts-method.md#review-another-fachrepo). Content identity alone does not establish compatibility with another protocol revision.
2. Use the single transport procedure in [Scale](../impacts-method.md#scale), including referenced Capability trees. For a first import, use an empty target folder. For takeover onto an existing target, review its update, referrers and recovery before replacement; never overlay an archive on existing work. Preserve Capability directories under their transport contract. Record each imported tree in the root `CONTEXT.md` beside clearance lines using the [import line](../templates/workspace.md#tree-clearance-and-imports), including the Fachrepo protocol pin. An open Vorgang continues on its old tree, or a new Vorgang names it as `vorgaenger` and supersedes it; no end is needed. Never rewrite its revision. Missing or different bound trees block execution under the [Capability contract](../capabilities.md#transport).
3. Keep imported revisions intact and run the applicable walks. For affected uses or source retirement outside the imported Core trees, apply the [Restructure reference and consumer checks](#restructure-mode). Customer-specific data uses declared source bindings; a changed process or bound rule requires a reviewed new Hauptprozess revision, not an unbound override.

## Walk test

Choose the branch established by form selection. For a selected Core Pipeline/Hauptprozess, a cold agent with no memory performs the Process Walk:

1. Open the root `CONTEXT.md`. Can it say where it is and how to advance a Vorgang from this one file?
2. Validate the selected workspace or Hauptprozess directory with `impacts validate`. Record the target and protocol revision; a different repository root is not automatically a Core workspace.
3. Open `vorgaenge/<vorgang>/CONTEXT.md`. Derive its current Arbeitsschritt or reached end under [Progress](../binding.md#vorgang-progress). Open the last entry's Arbeitsschritt `CONTEXT.md`: inputs, outputs, `pruefung`, routes and applicable human check are all named. For a Hauptprozess with no Vorgang yet, inspect its declared entry and mark Vorgang evidence as not yet demonstrated.
   Use `impacts hash` on declared attempt surfaces to check recorded hashes; this reads files and does not execute the Arbeitsschritt.
4. Every Hauptprozess body section holds the customer's facts, each labelled `verified`, `reported`, `hypothesis` or `open`. Read each Setup completion section and review its substantive case coverage, premises, expected results and recorded review results; record missing, bare or unsupported cases and remaining review gaps as open. Expected text alone does not establish a successful review or observed execution.
5. Report the loaded router, Arbeitsschritt and input paths. Aim for at most 8k tokens of actual task payload, not a minimum size. If the payload tokenizer is unavailable, report bytes/words and that limitation instead of an exact token-PASS.
6. Trace required conditions under [Hauptprozess setup completion](../templates/hauptprozess.md#setup-completion) and the [backward trace](../impacts-method.md#reverse-engineer-a-product-or-service). Separate design coverage from actual case satisfaction; missing work, checks or evidence leave a condition unproven. For calculations, trace one applicable output to its sanctioned rule and materialized inputs. For handoffs, trace one applicable transfer to its attempt-qualified origin and content digest. Mark absent features not applicable; declared features without a Vorgang remain unproven.
7. Where a human gate exists, inspect the required input/control evidence and the scope of its decision. Before opening it, the responsible harness applies the [gate rules](../binding.md#signals-and-human-gates) preflight. The later Gate output is checked against `pruefung`. A read-only review does not open or approve the Gate.

Apply [Readability and processing](../impacts-method.md#readability-and-processing) to the existing capture, processing, verification, change and handoff surfaces. On failure, follow [Reviewed correction](../impacts-method.md#reviewed-correction) at the authoritative wording or link. Keep genuinely missing evidence as a focused question; split files only when the existing form or task boundary earns it.

Where preparation during a wait is declared, exercise a representative case against [Work from prerequisites](../binding.md#work-from-prerequisites). Record its observed draft, blocker and continuation.

Run the [Knowledge Walk](references/formwahl.md#knowledge-walk) only when the topology uses `records/` or domain `grundlagen/`. This covers Record Libraries, Knowledge Bundles and Context Maps against their linked facts. A Context Map that links only Hauptprozesse uses their Process Walks. Umbrellas and System Maps test each child form through its applicable branch. Do not automate the walk or introduce a new checker.

## Guardrails

- Keep work at its existing home under [Tooling stop](references/formwahl.md#tooling-stop) while no Leistung, meaningful process boundary and declarable steps are established; form selection, not an arbitrary occurrence count, determines whether to build a Hauptprozess. Apply [Minimize](../impacts-method.md#minimize) to the particular supported bindings/checks the task needs.
- Stop question before any new term, field, folder kind or schema: name the existing structure that already does it.
- Before opening a real Vorgang, check that its Hauptprozess tree is cleared for real work ([clearance line and procedure](../templates/workspace.md#tree-clearance-and-imports)). This clearance does not overwrite the individual claims' evidence labels or supply missing source evidence.
